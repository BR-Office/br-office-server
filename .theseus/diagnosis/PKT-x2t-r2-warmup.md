# PKT-0108 — First-Execute warm-up of x2t PDF export: where it goes and what an in-process cut can gain

Decision note for plan x2t round 2, row P2 (decides P3). Measured 2026-11-04 on the factory VM (2 CPUs, 7 GB, shared
with other sessions: load 2.6–3.7 during the runs), native package 9.3.7-1 layout. The installed
`server/FileConverter/bin/x2t` is the source build of `core.base` 59458e06 (md5 27d8c02d…, same as the differential
oracle's mirror), not the package binary; `sdkjs/*/sdk-all.bin` snapshots present.

## Method

- Direct timing: `.theseus/oracle/perf/x2t-warmup.py <label> 5 <cwd> -- <cmd>`, median of 5, wall **and** child CPU
  (user+sys from `wait4`). Wall medians moved by up to ±300 ms between identical runs (shared VM), so **CPU time is
  the column that decides**; a gain counts only if ≥ 0.15 s in CPU and not contradicted by wall.
- V8 flags without rebuilding core: `.theseus/oracle/perf/x2t-v8flags-shim.c`, an `LD_PRELOAD` constructor that calls
  `v8::V8::SetFlagsFromString` (exported by `libdoctrenderer.so`) before V8 initialises; flags from `X2T_V8_FLAGS`
  (checked with `--trace-gc`, which prints). The preload is passed to the child only (`/usr/bin/env LD_PRELOAD=…`).
- Without snapshots / warmed snapshot: side layout in the scratch dir (copy of `bin`, symlink farm of the install,
  `cp -as` of `sdkjs` with the `.bin` files removed or regenerated by `x2t -create-js-snapshots`); the live server
  and other worktrees are never touched.
- Split: V8 inspector CPU profile of one conversion (`x2t-cpuprofile.js`, profiler started at the first pause and
  stopped after `asc_nativeGetPDF`), aggregated by call-tree subtree with `.theseus/oracle/perf/x2t-profile-tree.js`.
- Equality: every output PDF compared to the stock-snapshot output after `qpdf --qdf`; only `/CreationDate`,
  `/ModDate`, XMP dates, `/ID` and xref offsets differ (0 other lines) for all options below.

Inputs: `document-templates/new/en-US/new.{docx,xlsx,pptx}` → pdf.

## 1. Where the fixed cost goes (inside the first Execute)

Profiled time (inspector on, ≈ 1.45× real for docx, ≈ 1.0× for xlsx). Inclusive subtree times:

| Part | docx | xlsx | Document-independent? |
|---|---|---|---|
| `NativeCreateApi` → `asc_docs_api`/`spreadsheet_api._init` → `loadSdk` → `_onEndLoadSdk` | 110 ms | 43 ms | yes |
| Editor model init: `InitEditor` → `CDocument` (default `CStyles` 65, glossary `CStyles` 42, first `Paragraph`/`StyleCache` 29) | 142 ms | — | yes (default styles) |
| xlsx `ReadDefTableStyles` (SAX parse of the embedded default table-styles zip) + `WorkbookView._init` | — | 69 + 18 ms | yes |
| Reading the document (`ReadFromStream`/`PostLoadPrepare`/`CopyStyle`; xlsx `BinaryFileReader.Read`) | 106 ms | 26 ms | no |
| Layout (`RecalculateAllAtOnce`) | 29 ms | (in print) | no |
| `asc_nativeGetPDF` (print to PDF commands) | 60 ms | 60 ms | no |
| `(program)` (native: compile, IC misses, C++ callbacks such as font selection) | 230 ms | 212 ms | mixed |
| `(garbage collector)` | 91 ms | 67 ms | mixed |
| **profiled total** | **785 ms** | **506 ms** | |

Font matching (`GetSigPenalty`, `Base64.decodeData` of font data) is 50–70 ms self time spread across the above.
The warm-up is mostly **executing** JS that builds editor state (default styles, table styles, API objects), not
compiling it. The document-independent part — the ceiling of any snapshot taken after a warm-up — is
≈ 250 ms profiled ≈ **0.17 s real for docx** and ≈ 130 ms ≈ **0.13 s for xlsx**, plus an unknown share of
`(program)`/GC. pptx was not profiled (timing only).

## 2. Per-option gain (median of 5, ms; clean run 02:50–02:52 UTC)

| Option | docx wall / CPU | xlsx wall / CPU | pptx wall / CPU | Equal output |
|---|---|---|---|---|
| stock (`sdk-all.bin` on) | 914 / **540** | 827 / **529** | 1161 / **923** | — |
| no snapshots | 582 / 630 (+90) | 610 / 580 (+51) | 883 / 1017 (+94) | yes |
| `--no-lazy-feedback-allocation` | 505 / 546 (+6) | 480 / 514 (−15) | 750 / 884 (−39) | yes |
| `--no-opt` | 554 / 530 (−10) | 547 / 526 (−3) | 1429 / 895 (−28) | yes |
| `--single-threaded` | 488 / 481 (−59) | 555 / 496 (−33) | 1357 / 962 (+39) | yes |
| `--min-semi-space-size=16` | 898 / 500 (−40) | 565 / 438 (−91) | 825 / 930 (+7) | yes |
| `--max-lazy` | **crash (exit −4)** | 958 / 532 (+3) | 739 / 876 (−47) | docx: no output |
| warmed snapshot (`new AscWord.CStyles(true)` ×5 run at snapshot creation, bytecode kept), 2 interleaved rounds | 647 / 547, 423 / 506 vs stock 521 / 572, 627 / 555 (≈ −25…−49) | — | — | yes |
| docbuilder, 3 docx in one process vs 1 (persistent process, fresh context per document) | 1st doc 614 CPU, each next ≈ 640 CPU | — | — | sizes equal |

An earlier matrix (02:39–02:41) ran while the differential oracle was building/swapping and is discarded; it
showed the same signs (snapshots ≈ −0.1 s CPU, no flag ≥ 0.15 s) and the same `--max-lazy` docx crash.

Reading:
- Snapshots stay worth ≈ 0.05–0.1 s CPU (PKT-0065 found ≈ 0.1 s): keep them (packaging, PKT-0075).
- **No V8 flag gains ≥ 0.15 s** in CPU; the larger numbers (−59, −91) are single cells not seen on the other
  editors and within the run-to-run spread of the stock row (±30–50 ms CPU). `--max-lazy` is unsafe.
- A snapshot that only pre-compiles the init path (what `kKeep` buys) gains ≤ 0.05 s: compile is not the cost.
- A snapshot that keeps the **built** init state (default styles, table styles, API object) is bounded by the
  document-independent part above: ≈ 0.13–0.17 s (+ share of GC), below the plan's 0.2 s stop threshold and
  well below P3's 0.3 s target. It would also need sdkjs to reuse pre-built objects (styles are copied per
  document, `g_oTableId` registers them) and doctrenderer to snapshot a context whose objects reference native
  embeds (fonts, graphics, `window.native`), which `createJSSnapshots` (no embeds) cannot serialize.
- A persistent process that still makes a new JS context per document (docbuilder behaviour) gains **nothing**:
  each further document costs as much CPU as the first. Only a process that **keeps one warmed context**
  and resets the document in it removes the warm-up (≈ 0.5 s CPU of the ≈ 0.55–0.9 s).

## Fork prototype

No core-fork build was made. With the cache, any edit to `external/core` is a new tree key and a full core
rebuild (≈ 50–60 min on this VM, `x2t-build.sh`), and the measurable ceiling of the post-warm-up snapshot
(section 1) is already below the threshold that would justify P3. The no-rebuild prototype above (warm-up JS in
the snapshot via `-create-js-snapshots`) is the part of the lever that is reachable without native embeds.

## Recommendation for P3

**P3 should not implement an in-process warm-up cut** (no snapshot variant or V8 flag reaches 0.2 s; P3 context
says: stop). The remaining lever is a **persistent converter that keeps one warmed JS context per editor and
resets the document inside it** (FileConverter contract change, memory/isolation per conversion), which needs its
own diagnosis. Keep `sdk-all.bin` generation at install time.
